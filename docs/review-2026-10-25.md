## Product assessment

The strongest requirement survived implementation: explain Poland's grid without
claiming that cheap wholesale electricity means household savings. Keep the
single public dashboard, synchronized quarter-hour selection, official PSE
guidance, deterministic summaries, and inspectable source provenance.

The code deliberately uses RCE, not a day-ahead fixing. This is accurately
labelled, but remains a narrower feature than the research's day-ahead planner.
File storage substitutes for the proposed PostgreSQL foundation. It is adequate
for a local single-instance MVP, not a complete production archive.

Temporal was discussed but not implemented. UTC instants and Intl formatting
already avoid browser-local-time arithmetic in the frontend. This iteration
fixes actual DST presentation and selection defects without a dependency rewrite.
The backend's explicit current EU DST rule remains a maintenance assumption.

Deferred product ideas: event pages, anomalies and record detection, tomorrow
planning, price forecasts, tariff replay, accounts, notifications, Home Assistant,
emissions attribution, and cross-provider reconciliation. None is represented as
implemented or necessary for this corrective iteration.

## Architecture decisions

1. Keep normalization pure in `backend/lib/normalize.ml`; preserve explicit nulls,
   signed physical flows, publication revision selection, and renewable weighting.
2. Add a small day-selection module with an explicit today/history variant and
   one browser clock. Follow Warsaw midnight while retaining deliberate history
   selections. Date-tagged interval selection cannot leak into another day.
3. Make absence explicit: `latestIndex` returns null when no completed generation
   observation exists. An independently selected interval may still display
   available prices and flows; it is never labelled the latest generation reading.
4. Retain the existing store interface. Keep yesterday on a short cache TTL so
   midnight does not freeze late observations for six hours. Reject fractional
   official guidance codes instead of converting them into another category.
5. Separate deterministic UI fixtures from live integration checks. Test the
   92/96/100-quarter days directly, rather than assuming slot 48 is always noon.

The day-selection module earns its depth: removing it would redistribute clock,
calendar, and intent rules among callers. No generic repository framework or
large UI decomposition is warranted by this change. The normalizer already has
good locality and a small testable interface.

## Remaining limitations

- A persistence failure is still caught as a source failure in `Store.get`.
  A future focused change should separate acquisition success from archive-write
  success and test disk failures through a persistence seam.
- Remote pagination has a per-request timeout, not a total acquisition deadline.
  Slow multipage retrieval may outlast the browser's 60-second timeout. Existing
  retry and same-date cached fallback remain the recovery mechanism.
- The frontend validates field types but does not yet enforce complete semantic
  consistency of the whole day payload (unique sources, ordered contiguous slots).
- Source revision metadata is retained in raw responses, but there is no revision
  history explorer. The current UI does not reconcile PSE against ENTSO-E totals.
- Cache revisions have no retention budget. One API process per data directory
  remains required. Docker and remote CI execution are not verified by local tests.

Validation results are recorded in `VALIDATION.md`. Regression tests prove the
specified cases; they are not proof of complete upstream data correctness.

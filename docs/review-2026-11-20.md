# Dashboard review, 20 November 2026

Reviewed `d7b9bda` on `master`. The most important correctness change is to validate the country and measurement intervals in generation responses before saving them. The first performance change to measure is reuse of an already assembled day. The current cache avoids another download but rebuilds the response for every visitor.

## What the displayed numbers support

I independently compared the local day endpoint with its four saved provider responses. I matched Energy-Charts by source interval, PSE RCE and physical flows by quarter end, and active guidance by hour. For generation I summed the reported production series, excluding demand, trading, charging and percentage series. For flow I summed both directions on each of the six displayed borders.

| Warsaw date      | Source generation interval | Dashboard quarters | Values compared | Differences |
| ---------------- | -------------------------- | -----------------: | --------------: | ----------: |
| 14 June 2024     | 60 minutes                 |                 96 |             576 |           0 |
| 25 October 2026  | 15 minutes                 |                100 |             600 |           0 |
| 17 November 2026 | 15 minutes                 |                 96 |             576 |           0 |

The six fields were generation MW, demand MW, published renewable percentage, RCE, net physical import MW and guidance. All six had values throughout these samples. This checks arithmetic and time alignment against the same editions of the source data. The 96 historical quarters represent 24 hourly observations. Separately, the existing browser replay verifies formatting and selection for one complete quarter. These checks leave partial publications, further historical inventories, revisions and field performance outside the measured sample.

## Measured performance

The local measurements used the native OCaml API, a Vite preview of the production build and desktop Edge. Requests ran sequentially over loopback. Mobile results use a 390-pixel viewport on the same computer. No CPU or network throttling was applied.

| Measurement                                            | Result                                                                                                                                                                                   |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First request for 17 November                          | 4.79 s                                                                                                                                                                                   |
| Next eight requests for the same 96-quarter day        | 358 to 444 ms, median 412 ms                                                                                                                                                             |
| Nine requests for 25 October, a 100-quarter day        | 295 to 536 ms, median 351 ms                                                                                                                                                             |
| 100-quarter response                                   | 153,185 bytes of JSON, 16,155 bytes when gzipped locally                                                                                                                                 |
| Production assets                                      | 346,814 bytes JavaScript and 22,159 bytes CSS before compression                                                                                                                         |
| Navigation to visible cards on a warmed historical day | 1.01 s at 1440 pixels, 0.94 s at 390 pixels, one navigation each                                                                                                                         |
| Chart interaction                                      | 1,289 SVG descendants on the full day. Across 30 slider changes, two animation frames took a median of 31 to 32 ms. This includes waiting for both frames and is not an INP measurement. |

1. **Cache the assembled response.** Key it by day, source revisions and delivery/error state. Keep it bounded, invalidate it when a revision or fallback state changes, and preserve the provenance of each source. Aim initially for a warm local p95 under 100 ms over 100 requests. Measure time to first byte separately from download time. This target is proposed.
2. **Index PSE rows once.** In [Normalize.day](../backend/lib/normalize.ml), each quarter searches the flow rows twice for each border. A full 96-quarter day with 1,152 directional rows entails about 1.33 million row predicate checks for flows alone. Build an index by interval end and section, choosing the latest revision once. Use the same strategy for RCE and guidance. Compare old and new output field by field before comparing timings on 92-, 96- and 100-quarter days.
3. **Reduce transfer and repeat work.** The shipped [Nginx configuration](../deploy/nginx.conf) does not specify JSON compression or immutable cache headers for hashed assets. Check actual wire headers, enable compression where needed, and use revalidation for day responses. Consider a compact chart response only if transfer still matters. Keep the complete source detail available for inspection and export.
4. **Profile selection on a phone before replacing the charts.** Each selection updates the page and recreates formatters and chart elements. Reuse Polish date and number formatters and separate static series geometry from the selected marker if profiling confirms render cost. Keep keyboard selection immediate. Measure real input-to-paint latency and field LCP on low-end mobile devices.
5. **Set a snapshot policy before backfilling.** This workspace held 969 JSON files totalling 65,496,281 bytes at review time. Preserve distinct revisions and their first and last retrieval times. Measure duplicate content and growth per day before choosing compression, retention or a database. The current single-process cache has no cross-process coordination.

The current separation between acquisition, normalization and presentation is worth retaining. Concentrate validation at ingestion, own revisions and indexes in normalization, and make the UI consume explicit coverage and source intervals. The existing numerical replay provides a check on both calculation and presentation during these changes. Docker end-to-end behavior, Safari, physical phones, concurrent load and public-network latency still need dedicated measurements.
